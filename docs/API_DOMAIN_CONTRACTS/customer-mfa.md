# Customer login PIN API contracts

## Entries 316–317

**Status: SOURCE-TRACED.** Route: `server/routes/mfaRoutes.js` resolves tenant and applies per-IP throttles from `server/middleware/authRateLimiters.js`; there is no JWT because these endpoints are in login flow. Handlers are in `server/controllers/mfaController.js`; PIN normalization/hash/verification are in `server/services/mfaService.js`; user state is stored on `User`. No focused MFA controller test was found; acceptance test asserts development MFA bypass is disabled.

- `POST /api/mfa/customer/send-pin`: body requires `userId`; looks up user by ID and requires customer role (else 401). No active tenant equality is checked at this lookup; context does not scope it. A valid registered Kenyan phone is required. Generates cryptographically random four-digit PIN, stores bcrypt hash (cost 10), five-minute expiry, attempts zero and last-sent timestamp, then sends SMS. Resend within 30 seconds returns 429. SMS failure clears hash/expiry/attempts then propagates to centralized error handler. Per-IP throttle: 3 requests/15 minutes. Success 200 `{success:true,mfaRequired:true,userId,message}`; `devPin` and PIN-bearing message are included only when `MFA_DEV_MODE=true`.
- `POST /api/mfa/customer/verify-pin`: body `userId` and exactly four numeric digits `pin`; malformed request 400, unknown/noncustomer 401, no active PIN 400, expired PIN clears state and returns 401, five stored failures lock further attempts with 429 until new challenge. Incorrect PIN increments attempts, returns 401 and attemptsRemaining. Correct PIN clears PIN/lockout state, updates lastLoginAt, builds permissions/effective role, issues JWT (and auth cookie), writes audit log, and returns 200 with token and user object with password/PIN secrets omitted.
- Per-IP verification throttle: 6 requests/15 minutes, in addition to per-user 5-attempt ceiling. The IP limits use the repository's configured express-rate-limit store; distributed deployment behavior depends on that store configuration.

The PIN state save occurs before SMS delivery and is compensated if sendSMS throws. Verification saves user state before issuing/returning token and audit logging is awaited, so an audit failure can produce an error after the PIN has been consumed. Neither endpoint invokes an external provider during this documentation review; SMS delivery behavior is not live-verified. The current-user lookup is by globally unique User ID and does not compare the request tenant; document this as source behavior rather than a verified cross-tenant exploit.
