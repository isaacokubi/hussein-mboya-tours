# Admin payment API contracts

These contracts were traced from mounted routers through controllers and directly invoked guards/services. They have not been exercised against a running API or payment provider.

## Shared access controls

`server/routes/index.js` mounts `adminPaymentRoutes` at `/admin/payments`. The router runs `resolveTenant` → `protect` → `adminMiddleware` → `authorize("payment.manage")` before every route. Payment reads and writes use `mergeTenantFilter` or `tenantFilter`, and refund routes additionally run `guardPaymentRefund`. Standard authentication and tenant-selection headers/cookies are described in [the verified login contract](../API_VERIFIED_CONTRACTS.md).

## `GET /api/admin/payments`

- **Handler:** `adminPaymentController.getPayments`.
- **Request:** Optional `page` and `limit` query values are coerced to numbers; defaults 1/20; page minimum 1 and limit clamped 1–100. Optional `status` and `method` are copied directly into the tenant-scoped Payment query; this handler does not validate them against enums. No request body.
- **Data:** Finds tenant payments newest first, populates customer summary, booking summary plus tour summary, and hospitality booking summary. Separately counts matching payments.
- **Success:** HTTP 200 `{success:true,page,limit,total,payments}`.
- **Errors/effects:** Query errors forwarded to Express error handling; read only. The response does not include a `pages` field.

## `GET /api/admin/payments/reconciliation`

- **Handler:** `reconciliationController.getPaymentReconciliation`.
- **Request:** No route-specific query/body fields.
- **Data/algorithm:** Loads tenant payments, non-deleted bookings, invoices and commissions in parallel. Groups payments by booking, computes paid/refunded totals using completed/refunded payment states, compares booking and invoice paid/balance/status fields, calculates commission refund adjustments, and finds overpayments, missing invoices/receipts, duplicate transaction references, and orphan financial payments. Amount comparisons round to two decimals and use a one-cent tolerance for mismatch reporting.
- **Success:** HTTP 200 `{success:true,data:{summary,mismatches,missingInvoices,overpayments,commissionAdjustments,orphanPayments,missingReceipts,duplicateReferences,payments,generatedAt}}`.
- **Errors/effects:** Requires tenant context; query/aggregation failures are passed to error handling. The route performs reads and computes a report; it does not repair records or issue refunds.
- **Scale note:** It loads the tenant's relevant collections into application memory and reconciles them there. Large tenant datasets may require pagination or aggregation/offline reporting.

## `GET /api/admin/payments/stats`

- **Handler:** `getPaymentStats`.
- **Request:** No body/query fields.
- **Data/algorithm:** Tenant-scoped Payment aggregation groups by `status` and returns count, gross amount and `netAmount=max(0, amount-refundedAmount)` sums.
- **Success:** HTTP 200 `{success:true,stats:[{_id,count,amount,netAmount},...]}` based on Mongo aggregation output.
- **Errors/effects:** Tenant required; aggregation errors forwarded. Read only.

## `GET /api/admin/payments/analytics`

- **Handler:** `getPaymentAnalytics`.
- **Request:** No body/query fields.
- **Data/algorithm:** Tenant-scoped aggregation groups Payment by status and sums count and amount, sorted by count descending.
- **Success:** HTTP 200 `{success:true,analytics:[{_id,count,amount},...]}`.
- **Errors/effects:** Tenant required; read only; errors forwarded.

## `GET /api/admin/payments/export/csv`

- **Handler:** `financeExportController.exportPaymentsCSV`.
- **Request:** No body/query fields.
- **Data:** Finds tenant payments, populates booking number and customer name/email/phone, and maps transaction (receipt, checkout ID, or payment ID), booking, customer, phone, amount, status and created date to CSV rows.
- **Success:** HTTP 200, `Content-Type: text/csv`, attachment filename `payments-report.csv`; body is CSV generated by `json2csv`.
- **Errors/effects:** Requires tenant context; database/parser errors forwarded. Read/export only. Export includes phone and customer-identifying fields, so access to the route is sensitive and the resulting file should be handled accordingly.

## `GET /api/admin/payments/export/pdf`

- **Handler:** `financeExportController.exportPaymentsPDF`.
- **Request:** No body/query fields.
- **Data:** Gets system settings for company name, then queries tenant payments and populates booking number. Streams a PDF containing company title and each payment's receipt/ID, amount, status, booking and date.
- **Success:** HTTP 200 with `Content-Type: application/pdf` and attachment filename `payments-report.pdf`.
- **Error handling caveat:** `getSystemSettings()` is called before the handler's `try` block, so a rejection from that call is not caught by this function's `catch`; Express 5 async error propagation may still forward a rejected handler promise to application error handling. Database/PDF errors inside the `try` call `next(error)`.
- **Effects/privacy:** Read/export only; the exported document contains financial details.

## `GET /api/admin/payments/:id`

- **Handler:** `adminPaymentController.getPayment`.
- **Request:** Path `id` used in tenant-filtered `_id` query; handler does not explicitly validate ObjectId syntax.
- **Data:** Finds Payment and populates customer, booking and hospitalityBooking.
- **Success:** HTTP 200 `{success:true,payment}`.
- **Errors/effects:** 404 `{success:false,message:"Payment not found"}`; query errors forwarded; read only.

## `PATCH /api/admin/payments/:id/status` and `PATCH /api/admin/payments/:id`

Both declarations invoke `adminPaymentController.updatePaymentStatus`; they are two mounted aliases with identical controller behavior.

- **Request:** Path `id`; required body `status` string, trimmed and lowercased. Allowed values: `pending`, `processing`, `completed`, `failed`, `cancelled`, `refunded`. Optional `failureReason`, `confirmationReference`, `receiptNumber`, and `confirmationNotes` are read only in the relevant branches.
- **General branch:** For statuses other than `completed`/`refunded`, writes Payment status directly; when `failed`, also writes failure reason (default text, max 500 chars) and failedAt. This path does not use `canTransitionPaymentStatus`.
- **Completion branch:** Loads linked tenant Booking; permits manual completion only for provider `BANK` or `CASH`. Provider-integrated methods must be confirmed by provider callback/verification and return 409. A previously completed manual payment returns 409. Cash may require a receipt according to tenant settings. Calls `completeBookingPayment`, then stores manual confirmation actor/time/amount/currency/reference/notes on the Payment and saves again.
- **Refund status branch:** Setting `status:"refunded"` directly returns 409 and directs callers to refund workflow.
- **Success:** HTTP 200 `{success:true,payment}` for generic update; completion returns `{success:true,payment,booking}`.
- **Errors:** 400 invalid status or missing cash receipt; 404 missing payment/booking; 409 provider confirmation required, already confirmed, or direct refunded status rejected. Unexpected errors forwarded.
- **Consistency:** Completion's lifecycle call and subsequent manualConfirmation save are separate writes; source does not wrap them in one transaction.

## `PATCH /api/admin/payments/:id/refund`, `PUT /api/admin/payments/:id/refund`, `POST /api/admin/payments/:id/refund`

All three methods run `guardPaymentRefund` before `adminPaymentController.refundPayment`.

- **Request:** Path payment `id`; optional JSON `amount`; omitted amount means remaining refundable amount. Guard requires finite amount `>0` and not greater than `payment.amount - refundedAmount`. No other body property is used by this handler.
- **Guard:** Tenant-loads Payment; requires status `completed`; rejects refund status `processing` or `completed`; assigns the checked payment and amount onto `req` (controller calculates amount again from body/default).
- **Controller behavior:** Populates booking/customer; only `provider:"MPESA"` supports automated refunds; phone resolves from payment fields then customer phone. `submitMpesaRefund` verifies amount and original receipt/transaction ID, atomically changes refund status to processing with a conditional `findOneAndUpdate`, then calls Daraja. It stores provider conversation reference and marks booking refundStatus processing. Provider-call failure attempts to reset Payment to failed refund state; reset failure is swallowed before original error propagates.
- **Success:** HTTP 200 `{success:true,message:"Refund request submitted",refundResponse,refundAmount,payment}`.
- **Errors:** Guard 400 invalid ID/amount, 404 missing payment, 409 non-completed or refund already active/completed. Controller 400 non-completed/payment phone absent; 501 automated refunds unsupported for other providers. Provider and persistence errors go through central error handling. This response means a refund request was submitted, not that Daraja completed reversal.
- **Concurrency/side effects:** Conditional payment update claims the attempt to reduce duplicate concurrent reversals. Booking update follows provider acceptance and is not in a transaction with payment claim or provider. Reconciliation remains necessary for uncertain provider outcomes.

## Curl templates

These are source-shaped, unexecuted templates. Use a disposable tenant and staff identity with `payment.manage` permission.

```sh
curl -i "$API_BASE_URL/api/admin/payments?status=completed&page=1&limit=20" -H "Authorization: Bearer $TEST_TOKEN" -H "X-Tenant-Slug: $TEST_TENANT"
curl -i "$API_BASE_URL/api/admin/payments/reconciliation" -H "Authorization: Bearer $TEST_TOKEN" -H "X-Tenant-Slug: $TEST_TENANT"
curl -i -X PATCH "$API_BASE_URL/api/admin/payments/$PAYMENT_ID/refund" -H "Authorization: Bearer $TEST_TOKEN" -H "X-Tenant-Slug: $TEST_TENANT" -H 'Content-Type: application/json' --data '{"amount":25.00}'
```

## Frontend callers

`client/src/api/admin/adminPaymentApi.js` calls the list, stats, analytics, status (`PATCH /:id` alias), refund (`PATCH /:id/refund` with no body, so the server defaults to the remaining balance), reconciliation, CSV and PDF routes. The wrapper normalizes payment display fields from populated booking/customer/payment metadata. The export functions download the response Blob in the browser. No frontend caller for the detail route or the other refund method aliases was found in this wrapper; those mounted aliases remain available to authorized clients.
