# Driver operations API contracts

## Entries 239–243: driver dashboard and assigned-tour operations

**Status: SOURCE-TRACED.** `server/routes/driverRoutes.js` applies `protect`, `resolveTenant`, and `driverOnly` router-wide. Dashboard handler is `driverDashboard` in `server/controllers/driverController.js`; tour handlers are in `server/controllers/driverTourController.js`. Reads/writes involve tenant-scoped `Staff`, `Tour`, and `Booking` documents. No focused driver-controller tests were identified.

- `GET /api/driver/dashboard`: no request fields. Resolves driver staff profile by linked user or email among driver position aliases. It may repair `user`, position, role, active/status fields, or create a `Staff` profile if an email exists; missing email/profile returns 404. Finds up to 25 assigned tours, populates destination/guide/vehicle, and aggregates guest/booking totals for confirmed/assigned/ongoing/completed bookings. Returns 200 with `driver`, duplicate vehicle keys `vehicle`/`assignedVehicle`, status-derived `stats`, `tours`, and duplicate nested `data`. Errors go to central middleware.
- `GET /api/driver/assigned-tours`: resolves profile (404 if missing), reads up to 50 tenant tours assigned via `assignedDriver`, populates destination/guide/vehicle, adds booking guest counts, returns 200 `{success:true,count,tours,data}`. Unlike dashboard filter, this query does not include tours assigned only through legacy `driver` or `assignedTours` fields.
- `GET /api/driver/tours/:id`: tenant/profile scope; requires the tour's `assignedDriver` to match this driver. Returns populated `tour` in both top-level and `data.tour`; missing/unassigned returns 404.
- `GET /api/driver/tours/:id/guests`: same profile and assignment checks; missing profile 404, unauthorized/unassigned tour 403. Returns bookings in confirmed/assigned/ongoing/completed states, populates customer name/email/phone, newest first, in `{success:true,count,guests,data}`. This exposes guest contact details to the assigned driver.
- `PUT /api/driver/tours/:id/status`: body `status` must be `ongoing` or `completed`; anything else returns 400. Requires profile and assigned tour (404). `ongoing` is allowed only on the computed start calendar day and when current tour status is scheduled/upcoming. `completed` is allowed only on or after the computed end date and when status is ongoing. Updates `startedAt` or `completedAt`, and for completion `assignmentStatus`, saves Tour and returns it in `tour` and `data.tour`. Invalid transition/date returns 400; errors reach central middleware.

Dates use server-local calendar boundaries (`startOfDay`) for transition checks. Tour end is explicit `endDate` when available, otherwise start plus duration days (minimum one). No notification, customer booking status update, or payment mutation occurs in these handlers. No live driver account or route request was exercised.
