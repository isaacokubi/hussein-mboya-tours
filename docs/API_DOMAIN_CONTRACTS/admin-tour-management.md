# Admin tour detail, mutation, publication, restore, and resource assignment

## Shared route protection

These routes are declared in `server/routes/adminTourRoutes.js`, mounted at `/api/admin/tours` by `server/routes/index.js`, and protected by `resolveTenant` → `protect` → `adminMiddleware` → `authorize("tour.manage")`. Only active admin/super_admin pass the role middleware; the permission middleware handles explicit permission, platform wildcard, and admin compatibility grants. `Tour`, `Destination`, `Staff`, and `Vehicle` use tenant-scoped query middleware; handlers also use explicit tenant predicates in most writes. No branch filter exists.

## GET /api/admin/tours/:id (inventory 102)

`adminTourController.getTour` validates ObjectId and returns HTTP 400 `{success:false,message:"Invalid tour ID."}` if invalid. It queries non-deleted Tour by ID, then populates full destination, creator name/email, guide/driver name/email/phone and vehicle name/registration/model/capacity/type/status; `.lean()` returns a plain object. Missing or cross-tenant tour is 404 `{success:false,message:"Tour not found."}`. Success 200 `{success:true,tour}`. Query errors pass to `next(error)`. Read-only. Frontend `getTour(id)` in `client/src/api/adminTourApi.js` unwraps `.tour`; this method is used by tour edit flows. No dedicated handler contract test found; the opt-in first-tenant test exercises cross-tenant detail denial.

## POST /api/admin/tours (inventory 103)

Pipeline: `validateFutureTourDate` → `upload.array("images",10)` → `tourCrudController.createTour`. Body is JSON or multipart form; controller allowlists mutable Tour fields: `title`, `description`, `shortDescription`, `slug`, `tags`, `category`, `destination`, `country`, `location`, `meetingPoint`, `coordinates`, `duration`, `durationDays`, `durationDetails`, `date`, `startDate`, `endDate`, `capacity`, `price`, `agentPrice`, `discount`, `discountPrice`, `pricingRules`, `depositType`, `depositRequired`, `taxEnabled`, `taxCategory`, `taxMode`, `taxRate`, `highlights`, `inclusions`, `exclusions`, `languages`, `minimumAge`, `maximumAge`, `difficulty`, `itinerary`, `availability`, `availabilitySettings`, `cancellationPolicy`, `bookingDeadline`, `instantBooking`, `featured`, `available`, `published`, `status`, and `seo`. Unknown keys are dropped.

`normalizedPayload` requires nonblank title/description/country/location and destination, date or startDate, and finite nonnegative price. Duration parses the first numeric component, floors it, and requires 1–365 days; endDate cannot be invalid or before start. Capacity is coerced with fallback 20 and minimum 1; discount is coerced and clamped 0–100; depositType must be fixed/percentage. Stringified list fields (tags, highlights, inclusions, exclusions, languages, itinerary, availability, pricingRules) are JSON-parsed. Boolean strings for published/available/featured/instantBooking/taxEnabled must be true/false. Defaults: status upcoming, published false unless provided, available true except literal boolean false, availabilitySettings from capacity, creator from user, not deleted. Schema hooks also normalize duration and generate slug.

The future-date middleware runs **before** Multer. For multipart requests, `req.body` may not yet be parsed, so that middleware can miss a past date; JSON requests are checked. `createTour` does not independently reject past dates, though schema validation handles date shape and other constraints. Additionally, the controller accepts `startDate` as satisfying its manual date-presence check, but `Tour.date` is schema-required and the normalizer does not copy `startDate` into `date`; a request omitting `date` can therefore fail Mongoose validation. This is a source-observed validation gap.

Uploads accept up to 10 files in field `images`, each max 5 MiB; filename extension/MIME must match JPG/JPEG/PNG/WEBP/PDF, and configured uploads use tenant-specific Cloudinary storage. Images become featuredImage (first) and gallery (rest); PDF files can pass middleware but `normalizedPayload` only incorporates `file.path` without distinguishing PDF, leaving schema/use compatibility dependent on Cloudinary result. When Cloudinary is unavailable, non-file multipart fields can pass but an included file fails 503. Multer errors are handled by app middleware.

Database work uses `mongoose.startSession()` and `session.withTransaction`: tenant destination must exist and not be deleted; requested guide/driver/vehicle must be active, tenant-owned, available, and not assigned to another active overlapping tour. Tour insert and associated resource status/assignment writes commit together. Resource checks or transaction failures are forwarded to Express. After commit, it rereads populated Tour and returns 201 `{success:true,message:"Tour created successfully.",data,tour}`. If a Cloudinary upload succeeds but the transaction fails, this controller has no asset cleanup path. Transaction operation requires a transaction-capable MongoDB deployment; the live topology was not verified. Frontend callers include `createTour` in `adminTourApi.js` and `CreateTour.jsx`. `server/tests/firstTenantAcceptance.integration.test.js` tests a tenant tour create when its MongoDB opt-in is configured; the default suite skips that integration.

## PUT /api/admin/tours/:id (inventory 104)

Pipeline: `validateTourCommand()` → upload parser → `tourCrudController.updateTour`. Validator rejects blank provided title/description; invalid/negative price, capacity less than 1/non-integer, discount outside 0–100, negative deposit, invalid depositType, duration outside 1–365, invalid date, and past date/startDate (it runs before Multer, same multipart parsing limitation). Controller separately validates ID (400) and existing non-deleted tenant Tour (404). Any assignment key (`assignedGuide`, `assignedDriver`, `assignedVehicle`, `guide`, `driver`, `vehicle`) is rejected 400; use dedicated resource routes.

Body uses the same mutable field allowlist and normalization as create, merged over the existing Tour; fields not supplied are preserved. It removes tenantId and createdBy from update payload. It updates tenant-owned Tour with validators, populates destination/guide/driver/vehicle, and returns HTTP 200 `{success:true,message:"Tour updated successfully.",data,tour}`. Errors go to `next`. Uploads can create unreferenced Cloudinary assets if later validation/database write fails. Caller `updateTour` in `adminTourApi.js` / `EditTour.jsx`.

## DELETE /api/admin/tours/:id (inventory 105)

Body may provide optional `reason`; default is `"Tour deleted/cancelled"`. Invalid ID 400. `cancelTourAndBookings` uses a Mongo session transaction; it rejects missing/cross-tenant tour (404) and completed tour (409), loads active non-deleted bookings excluding cancelled/refunded/completed, releases each booking's capacity, marks bookings cancelled with cancellation metadata, requests refund review when amountPaid > 0 (without initiating a provider refund), otherwise sets paymentStatus cancelled; marks Tour cancelled/unavailable/unpublished/deleted, releases assigned resources, and emits in-app notifications for affected users within the transaction. Returns 200 `{success:true,message,data:tour,bookingsAffected}`. Transaction/provider behavior is not a live-tested refund. Caller `deleteTour` in `adminTourApi.js`; UI in `ManageTours.jsx`.

## PATCH /api/admin/tours/:id/publication (inventory 106)

Body `published` required as boolean or string `"true"`/`"false"`; other forms return 400. Valid ID required (400); tenant non-deleted Tour missing gives 404. Updates only published (Mongoose validators), populates destination/assigned resources, returns 200 `{success:true,message,data,tour}`. No other state changes. Errors forwarded. Caller `setTourPublication` in `adminTourApi.js`.

## PATCH /api/admin/tours/:id/restore (inventory 107)

No body fields read. ID invalid is 400; only a tenant tour with `isDeleted:true` is eligible, otherwise 404 `{success:false,message:"Deleted tour not found."}`. Sets isDeleted false and clears deletedAt/deletedBy when those paths exist, saves, then if it has an assigned vehicle, loads tenant vehicle and sets available/clears assignedTour, saves separately. Populates assigned guide/driver/vehicle and returns 200 `{success:true,message:"Tour restored successfully.",tour}`. The Tour and Vehicle writes are not transactional; a second write failure can leave partial state. It does not restore guide/driver availability. Errors forwarded. No frontend restore caller found during this review.

## PATCH /api/admin/tours/:id/guide, /driver, /vehicle (inventory 108–110)

All three paths use the same `assignTourResourcesSafe` handler; the path suffix does not constrain which resource body fields can change. Optional JSON keys are `guideId`, `driverId`, `vehicleId`; omitted fields keep current assignments and null/empty string clears a field. Invalid ID gives 400; missing/deleted tenant tour 404. Each non-null resource ID must be valid; resource must belong to tenant, be active and not deleted, be available unless already assigned to this tour, and not overlap another active tour using that same role. Conflicts return 409 `RESOURCE_DOUBLE_BOOKED`; bad/inactive/cross-tenant resource returns 400; unavailable resource returns 409.

The handler uses a Mongo transaction to save Tour assignments, free replaced staff/vehicle, set newly assigned Staff busy and add tour ID, and set Vehicle assigned. Success HTTP 200 `{success:true,message,data}` with populated tour. After commit it best-effort queues `tour.resources.assigned` webhook; queue errors are logged but do not fail the response. Mongo errors go through `next`. The middleware does not verify route suffix against body, so a PATCH to `/guide` may update driver and vehicle too. No dedicated frontend caller for these exact three paths was found; tour resource assignments also occur during create, and the backend admin API exposes these routes.

## Transaction and test boundary

Create and resource assignment use `withTransaction`; delete/cancellation also uses a session transaction. This requires a replica set or supported sharded MongoDB topology, not standalone MongoDB. The repository enforces MongoDB 4.2+ but does not establish the live deployment topology. Tests cover tour lifecycle transaction behavior behind an opt-in Mongo test and are skipped without its URI. Route-level negative cases, multipart past-date validation, Cloudinary orphan cleanup, and assignment suffix/body mismatch are not covered by the located tests.
