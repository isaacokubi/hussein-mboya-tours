# Airport transfer API contracts (entries 166–173)

Router: `server/routes/airportTransferRoutes.js`, mounted under `/api/airport-transfers` in `server/routes/index.js`. This router does not install router-wide tenant/auth middleware; access is route-specific and controllers construct tenant filters from `req.tenantId || req.user.tenantId`.

## GET catalog (entry 166) and GET `/:id` (entry 173)

Public routes with no explicit auth middleware. List accepts optional `airportCode` (trimmed/uppercased) and `direction` (passed through); returns active current-tenant transfers sorted airportCode, price, name as `{success:true,data:[...]}`. Detail uses `id` and active tenant filter; missing returns 404 `{success:false,message:"Transfer service not found."}`, otherwise `{success:true,data:item}`. Neither checks malformed ObjectId explicitly; DB cast errors are centralized. If no tenant context, controller filters `tenantId:null`; no cross-tenant fallback is intended, but public tenant resolution/configuration determines whether a catalog appears.

## Admin catalog

- **GET `/admin/catalog` (167):** `protect` → `managerOnly` → `listAdminTransfersSafe`; optional `status` exact filter; requires tenant (400 if missing); returns all matching tenant transfer docs newest-first/sorted `{success:true,data}`. Errors forwarded.
- **POST `/admin/catalog` (168):** `protect` → `managerOnly` → `createTransfer`. Body is spread into AirportTransfer create, then name/vehicleType trimmed, tenant and audit users overwritten. Controller requires nonempty name and vehicleType, passengerCapacity >=1, price >=0 (400 otherwise). Success 201 `{success:true,data:item}`. Schema validation/database errors forwarded. Since source body is spread, accepted fields are constrained by Mongoose strict schema rather than a controller allowlist.
- **PATCH `/admin/catalog/:id` (169):** same manager guard; tenant-scoped find; missing 404. Applies only allowlisted fields name, airportName/code, direction, pickup/dropoff, vehicleType, passenger/luggage capacity, pricingModel, price, currency, durationMinutes, amenities, operatingHours, notes, status; updates audit user and saves. Success 200 `{success:true,data:item}`. No explicit ID validation; schema/DB errors centralized.

## Booking APIs

- **POST `/bookings` (170):** `protect` → `createEnhancedTransferBooking`; any authenticated tenant role can pass route middleware, with customer-specific rule in controller. Requires tenant and `transferId` (400), active tenant transfer (404). `passengers` defaults 1 and must be integer 1..capacity; `luggage` defaults 0 integer 0..capacity; pickup time required/valid; optional flight arrival/departure times must parse; childSeats/boosterSeats nonnegative and combined <= passengers. Resolves/creates Customer for user using supplied or profile identity; customer role without phone fails 400. Price is fixed or per-passenger according to transfer pricingModel, plus caller-supplied numeric-coerced taxes/fees; no positivity validation on taxes/fees here. Persists pending AirportTransferBooking and then creates/ensures hospitality invoice. Success 201 `{success:true,data:booking,invoice,paymentRequired:totalAmount>0}`. Booking creation and invoice creation are not one transaction: invoice failure can return an error after booking persisted; retry may duplicate booking. No payment is initiated.
- **GET `/bookings` (171):** `protect`, then controller permits customer or staff roles admin/manager/tour_manager/tourmanager/agent/super_admin/superadmin; otherwise 403. Requires tenant (400). Optional status filter unvalidated; customers are filtered to their own `user`, staff see tenant rows. Returns `{success:true,data:[...]}` sorted pickup date then newest, enriching transfer/customer/user/vehicle/driver from separate tenant-filtered reads; inconsistent/dangling references are filtered out. No pagination.
- **PATCH `/bookings/:id` (172):** `protect` → `paymentMutationGuard` rejects any body containing `paymentStatus` (403) → controller. Tenant booking missing 404. Customers may only edit `specialRequests` and only their own reservation; staff from the same explicit role set may edit. Customer status/resource/internal notes changes are forbidden. Staff status transitions are constrained: pending→confirmed/cancelled/no_show; confirmed→assigned/cancelled/no_show; assigned→driver_en_route/cancelled/no_show; driver_en_route→picked_up/cancelled/no_show; picked_up→completed/cancelled; terminal statuses cannot transition (409). Vehicle/driver IDs validate (400); selected resources must be active, tenant-owned and eligible (409); conflict check rejects another active booking within ±2 hours (409). Updates specialRequests; internal notes staff-only; saves and returns `{success:true,data:booking}`. No refund/provider call occurs.
