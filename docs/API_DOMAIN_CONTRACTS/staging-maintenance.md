# Restricted staging maintenance endpoints

## Entries 312–314

**Status: SOURCE-TRACED.** Routes are mounted by `server/routes/internal/stagingSuperAdminBootstrapRoutes.js` and target `global_tours_test` only. They have no JWT middleware; access instead requires exact runtime environment checks, high-entropy header tokens compared with `timingSafeEqual`, and rate limits of three requests per hour. Relevant tests: `server/tests/stagingQaSeed.test.js` and `stagingTenantAdminPasswordReset.test.js`. Do not call these against production or use live data.

All endpoints return 404 unless `NODE_ENV=production`, `DEPLOYMENT_ENV=staging`, and `STAGING_DATABASE_NAME=global_tours_test`. Seed and verify require `X-Staging-QA-Seed-Token` matching `STAGING_QA_SEED_TOKEN` (minimum 32 characters); mismatch/missing token is 403. These are application-level gates, not authentication middleware.

- `POST /api/internal/staging/seed-qa`: no body. In-process concurrent call returns 409; after successful invocation the handler becomes one-shot for that process and returns 404 thereafter. It also requires the connected database name to be `global_tours_test`. Calls `runStagingQaSeedOnce`, which validates the configured Mongo URI/host, rejects production hostnames and `husseindb`, verifies a fixed tenant/admin, and creates or updates deterministic synthetic QA customer/destination/tour/booking records. The booking remains pending/unpaid; no payment is run. Success 200 `{success:true,...counts}`; failure 500 with fixed error code.
- `GET /api/internal/staging/verify-qa`: no body/query. Runs environment/database/tenant/fixture/reference/payment-state checks and returns 200 `{success:true,...verification}`; mismatch/failure 503 fixed error. The shared limiter is used with seed route.
- `POST /api/internal/staging/reset-tenant-admin-password`: requires `X-Staging-Tenant-Admin-Reset-Token` matching `STAGING_TENANT_ADMIN_RESET_TOKEN` (minimum 32 chars); body `password` length 8–128, containing uppercase and digit. Request target must match hard-coded staging admin email and tenant environment variables, otherwise 404. Revalidates staging Mongo URI via `validateStagingSuperAdminBootstrapTarget`, opens a separate connection, confirms database is `global_tours_test` and not `husseindb`, loads only the exact email+tenant user, hydrates and saves through Mongoose so password hashing hooks run, and clears password reset/login PIN/lock counters. One-shot per process; busy returns 409, invalid password 400, bad token 403, success 200 `{success:true,reset:true}`, internal failure 500. Connection closes in `finally`.

The durable QA seed marker makes seed reruns report already complete across process restarts. The in-process one-shot flags and rate limits are per process and are not distributed locks. Secrets are supplied only via runtime environment; never add their values to documentation. Test coverage uses injected dependencies and does not prove a live staging deployment is configured correctly.
