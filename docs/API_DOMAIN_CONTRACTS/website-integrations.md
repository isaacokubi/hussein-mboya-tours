# Website integration and lead API contracts

## Entries 301–311

**Status: SOURCE-TRACED.** Router: `server/routes/integrationRoutes.js`; key guards and origin binding: `server/middleware/integrationAuth.js`; handlers: `server/controllers/integrationController.js` and `websiteLeadController.js`. Models include `WebsiteIntegrationKey`, `WebsiteIntegrationEvent`, `Organization`, `Tour`, `Booking`, `Customer`, `Lead`, `Invoice`, and notifications. Routes under `/v1` share a limit of 120 requests per 15 minutes, keyed by IP and a truncated integration-key header; standard rate-limit headers are enabled. The management `/keys` and `/leads` routes are outside that limiter.

### Key management

- `POST /api/integrations/keys`: JWT and `settings.manage` permission; controller also requires admin/super role or permission. Body `name`, `environment`, `allowedOrigins[]`, `permissions[]`. Name defaults “Existing Website”; origins are trimmed/capped at 20; permissions default to booking:create/customer:create/tour:read if omitted/empty. Only exact `environment:"test"` produces test; other values become live. Live key requires at least one origin (400). Generates a random secret and public site key, stores SHA-256 hashes/prefix only, returns 201 including the secret once, site key, and safe integration metadata. No secret is returned later.
- `GET /api/integrations/keys`: same guards; returns tenant key records with name/prefix/publicKey, active/environment/origins/permissions/use metadata, excluding private hash/secret.
- `DELETE /api/integrations/keys/:id`: same guards; tenant-scoped active key is revoked (`active:false`, `revokedAt`). Missing/already revoked returns 404; success `{success:true,message}`.

### Public/private v1 key authentication

`requirePublicIntegrationKey` reads `X-Public-Integration-Key` or `?siteKey=`, requires minimum length 20, hash-matches active, non-revoked record, requires active/trial Organization, and requires a browser Origin exactly matching one configured origin. `requireIntegrationKey` reads `X-API-Key` or `X-Integration-Key`, minimum 32 chars, and applies origin restrictions if an Origin is present. Both attach tenant/key/permissions/environment context, increment key usage and execute handler in tenant AsyncLocalStorage. Permission middleware requires the exact capability. Failures include 401 missing/invalid key and 403 inactive tenant/origin/permission. Public key is not a replacement for origin validation; private API keys should not be exposed in browsers.

### Read/widget/booking routes

- `GET /api/integrations/v1/config`: public site key plus `tour:read`; returns tenant branding/support/currency plus endpoint names. Reads Organization and tenant system settings.
- `GET /api/integrations/v1/tours`: public key + `tour:read`; query `limit` defaults 50, clamps 1–100; `search` trimmed/capped 120. Returns published, available, non-deleted scheduled/upcoming/ongoing tours and selected public price/date/booking fields, ordered featured/popularity/newest.
- `GET /api/integrations/v1/widget.js`: public key + `booking:create`; reads optional query `siteKey`; responds JavaScript with `Cache-Control:no-store`. Generated connector discovers form fields, excludes sensitive-looking/password/file values, submits to v1 bookings, and uses browser Origin/key checks. It is dynamically generated code, not a separate persistent asset.
- `POST /api/integrations/v1/bookings` (public key) and `POST /api/integrations/v1/server/bookings` (private key): both require `booking:create` and share `createExternalBooking`. Body supports tour ID or slug, travelDate, guest count, customer contact/identity, pickup/hotel/room, emergency/special requests, payment method and external booking ID/reference. Tour/date/customer phone are required; date cannot be past; guest count is normalized to 1–100. Capacity is checked and reserved, amount is calculated server-side, optional `customer:create` permission allows tenant customer lookup/upsert, then a partner-source pending Booking, invoice/upsert event and admin notifications are created; SMS/WhatsApp are best-effort. Success 201 returns booking summary and optional customer. External ID replay checks integration key + event type + ID and returns existing booking with `duplicate:true`, recording a duplicate event. Failure after capacity reservation attempts `releaseSlots`; a rejection event is best-effort. This is compensation, not a transaction; event, booking and notification writes can fail at different points. No payment is collected by this endpoint.
- `POST /api/integrations/v1/leads`: public key + `lead:create`; body accepts customer/contact identity, optional tour/date/guest count/message/source/page/referrer/UTM/custom fields/marketing consent. Phone required; supplied email validated. Optional tour is linked only when found public/published/available. PII/custom strings are trimmed/capped; custom fields drop keys that look like card/CVV/secrets/tokens/authorization. Creates tenant Lead and returns 201 with a limited lead view. It does not create a booking.
- `GET /api/integrations/leads`: JWT + `settings.manage`, tenant list; query `limit` clamps 1–200 (default 50), optional status and search across name/phone/email/company; newest first with tour label.
- `PATCH /api/integrations/leads/:id`: same management guards; updates allowlisted status/message/contacted date/converted booking fields only, tenant-scoped; missing record 404 and success returns updated lead. Model validation governs allowed status values.

No live browser-origin test or external booking was executed. The public-origin model reduces arbitrary browser reuse but does not make a published site key secret. Key creation allows supplied permission strings; actual endpoints remain gated by exact permission checks. Integration event/booking idempotency covers duplicate external IDs only when supplied and is not a general request idempotency guarantee.
