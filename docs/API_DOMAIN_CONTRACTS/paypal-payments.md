# PayPal booking payment contracts

## Entries 359–361: webhook, order creation and capture

**Status: SOURCE-TRACED.** Router `server/routes/paypalRoutes.js`; controller `server/controllers/paypalController.js`; provider client/signature verification in `server/services/paypalService.js`; persistence in `Payment`, `PaymentGatewayConfig`, and `PaypalWebhookEvent`; booking completion uses `paymentLifecycleService.js`. Create/capture require tenant resolution and JWT, with 10 requests per 15 minutes per endpoint limiter. Webhook route is unauthenticated at user level and verifies provider signature through PayPal API. Tests in `server/tests/paypalPaymentIntegration.test.js` cover API root selection, token/request behavior, signature verification shape and currency availability/source contracts; no live provider transaction was run.

- `POST /api/payments/paypal/orders`: body `bookingId`; authenticated owner required. Tenant setting must enable validated PayPal (409); booking must exist, be owned, active and unpaid (404/403/409). Server calculates outstanding payable amount and uses booking/settings currency; supported currencies are explicit allowlist. Reuses an existing pending/processing order if provider order ID and approval URL exist; otherwise blocks retry with 409. Requires tenant gateway config validated for sandbox/production; production is disabled until sandbox lifecycle verification timestamp exists. Creates local processing Payment before provider call with stable request ID. Provider order uses CAPTURE intent, payment/booking metadata and trusted client return/cancel URLs. On valid CREATED response persists order/approval URL and booking payment reference/status, returns 201 `{success:true,orderId,url,status}`. A definite provider failure marks Payment failed; uncertain timeout/abort retains processing record and blocks blind retry. Errors return provider status or 502 with generic text. Currency mismatch/unsupported is 409; no outstanding amount 400.
- `POST /api/payments/paypal/orders/capture`: body `orderId` (nonempty, <=80 chars). Finds tenant Payment, checks payment/customer and booking ownership, is idempotent for already completed records, loads the original configured environment, independently retrieves/verifies PayPal order ID, custom payment ID, amount, currency and merchant, then requests capture with stable PayPal request ID. VOIDED/DECLINED is persisted cancelled/failed and returns 409. No completed capture returns 202; mismatched capture amount/currency returns 409; valid capture calls `completeBookingPayment` and returns paid/status/paymentId. Timeout/abort returns 202 processing for reconciliation/retry. Other errors go to central middleware.
- `POST /api/payments/paypal/webhooks/:tenantId/:environment`: provider endpoint; validates tenant ObjectId, normalized sandbox/production environment, event ID and type; loads tenant gateway config; verifies signature by calling PayPal's `/v1/notifications/verify-webhook-signature` with transmission headers, configured webhook ID, and event. Invalid signature 400; invalid/inactive configuration 404. Event ID is tenant-scoped and stored in `PaypalWebhookEvent`; duplicates already processed/ignored/processing return 200 duplicate. Stale processing leases (>5 min) and failed/received events can be reclaimed. Unsupported event types are marked ignored and acknowledged. `CHECKOUT.ORDER.VOIDED` marks pending/processing local payment cancelled. `PAYMENT.CAPTURE.COMPLETED` requires related order ID, matching local payment/environment and a second provider GET; verifies purchase unit custom_id, capture ID/status, both amount/currency values and configured merchant before tenant-scoped booking lookup and `completeBookingPayment`. First sandbox verified lifecycle stamps gateway config. Success 200; unmatched local payment or processing error returns 500 and event is marked failed for retry. Logs only a sanitized code; provider secrets/bodies are not echoed.

Webhook idempotency is backed by event uniqueness/lease state plus payment lifecycle behavior. Mongo transaction guarantees depend on `completeBookingPayment` and transaction-capable deployment; deployment topology was not verified. Exact user/IP webhook allowlisting is not implemented here; provider signature verification is the trust control. Credentials are encrypted/configured in gateway records and are not included in docs. No real orders, capture, or webhook were sent.
