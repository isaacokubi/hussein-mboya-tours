# Hospitality payment API contracts

## Entries 283–288: M-Pesa, Stripe card, bank transfer and payment history

**Status: SOURCE-TRACED.** Routes in `server/routes/hospitalityPaymentRoutes.js` all require `protect`. Controller: `server/controllers/hospitalityPaymentController.js`; business logic: `hospitalityPaymentLifecycleService.js` and `hospitalityInvoiceService.js`; M-Pesa calls `mpesaService.js`; Stripe uses a direct authenticated `fetch` call. Records are in `Payment`, `HotelBooking` or `AirportTransferBooking`. Existing test evidence includes `server/tests/hospitalityPaymentLifecycleIntegration.test.js` for completion and `hospitalityFinanceIntegrity.test.js` for source-contract coverage; these do not live-verify Stripe/Daraja.

Shared access rule: `type` selects `hotel` or `airport_transfer`. Booking lookup is constrained by tenant and booking ID. `assertHospitalityPaymentAccess` permits booking owner/customer or roles admin/super_admin/superadmin/manager/tour_manager/tourmanager/agent. Invoice creation/synchronization is an additional database side effect.

- `POST /api/hospitality-payments/mpesa`: body `type`, `bookingId`, optional `amount`, optional `phoneNumber`. Invalid type 400; missing booking 404; access denied 403; no balance/invalid amount/phone 400. Amount defaults to current payable balance and must be 1..payable. If an existing pending/processing Payment exists, returns its checkout ID/amount/payment ID instead of initiating another push. Otherwise calls `initiateStkPush`, creates a pending MPESA `Payment`, and returns provider identifiers plus payment/booking info (default 200). A provider request can have an ambiguous outcome before Payment persistence; no idempotency key is supplied here.
- `POST /api/hospitality-payments/card`: same booking selector/access checks; no request amount is used. Creates Stripe Checkout for current payable amount using `STRIPE_SECRET_KEY`, `DEFAULT_CURRENCY` or booking currency, and `CLIENT_URL`; success/cancel URLs point to client pages and metadata binds booking/type/user/reference. Missing balance returns 400; absent config or Stripe errors go to central middleware. Creates pending `Payment` after Stripe session creation; returns 201 `{success:true,data:{sessionId,url,paymentId,amount,currency}}`. Stripe session could exist if local persistence fails.
- `GET /api/hospitality-payments/card/verify/:sessionId`: retrieves the session directly from Stripe. Metadata must contain supported type and booking ID (400); mismatching user is 403 unless staff; tenant booking and matching local Stripe Payment must exist (404); booking access is checked. Non-paid returns `{success:true,paid:false,status}`; expired session marks local payment failed through lifecycle service. Paid session amount in cents must match current payable balance or returns 400. Successful verification calls completion service and returns paid state plus payment/booking/paidAmount/balance. The provider query, metadata, local payment linkage, amount and current balance are checked; this is a polling verification endpoint, not webhook processing.
- `POST /api/hospitality-payments/bank`: body `type`, `bookingId`, optional `amount`, required nonempty `reference`, optional `notes`. Amount defaults to payable and must be finite, >=1, and <= payable. Creates pending BANK Payment with reference and returns 201 containing payment ID/reference/amount/status. This is a customer-submitted claim, not proof of bank settlement.
- `POST /api/hospitality-payments/bank/:paymentId/confirm`: requires one of the hard-coded staff roles (403 otherwise), tenant payment and matching hospitality booking (404). `approved === false` marks failed with optional reason; every other value, including omitted `approved`, proceeds to complete payment using stored amount/reference and optional transactionId. Returns lifecycle payment/booking/paidAmount/balance. This endpoint is a manual financial authorization point; authorization uses role strings rather than a dedicated permission.
- `GET /api/hospitality-payments/:bookingId?type=hotel|airport_transfer`: loads tenant booking, checks owner/staff access, ensures/synchronizes invoice, lists tenant payments newest first, and derives paid amount from completed/refunded rows net of refundedAmount; returns booking, invoice, payments, paidAmount and nonnegative balance. Invalid type 400, missing booking 404, denied 403.

The completion/failure service uses `mongoose.startSession()` and `withTransaction`: it updates payment and booking status, syncs invoice payment state, posts to the operational ledger, and may create customer notification. Completion returns already-completed records idempotently, checks amount against remaining balance, and prevents overpayment within the transaction. This requires transaction-capable MongoDB deployment; no production topology verification is implied. Initiation and Stripe session creation themselves are not inside that transaction. No real payment was performed.
