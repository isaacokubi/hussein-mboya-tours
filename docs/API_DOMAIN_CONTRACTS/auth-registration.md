# Customer registration contract

`POST /api/auth/register` (inventory 178) runs `resolveTenant` then `register`; it is unauthenticated but must resolve a tenant. The resolver honors active tenant host/domain or explicit tenant selector and configured public tenant rules; unresolved explicit selectors return 404. No role/branch authorization or registration rate limiter is mounted here.

JSON body requires `name`, `email`, `phone`, `password`. Email is trimmed/lowercased and must match a basic non-whitespace address pattern. Phone is stringified/trimmed and must be exactly 10 digits (no country-prefix handling). Password must be at least 8 characters with a digit and uppercase letter. Tenant context is required (400 otherwise). The controller checks for existing tenant User by normalized email or phone; duplicate returns 400 with corresponding message. It resolves Role `customer`, then creates active, verified customer User with role/legacyRole customer and tenantId. User model save middleware hashes password. It records a SecurityLog registration event and returns HTTP 201 `{success:true,user:{_id,name,email,phone,role,tenantId,permissions:[],profileImage,status,isVerified,loyaltyPoints,referralCode,lastLoginAt,createdAt},message}`. Registration does not return JWT, set auth cookies, or create a session; user must log in afterward. It sets `isVerified:true` despite no email/phone verification flow in this handler.

Security-log/database errors are caught and passed to centralized handling; since User creation precedes SecurityLog write without a transaction, a logging failure may return an error after the account was created. Client registration API/pages should be checked for the exact 10-digit phone and password constraints. `firstTenantAcceptance.integration.test.js` contains tenant registration cases, but the full suite skipped the MongoDB-backed first-tenant integration group in this run; source contract only was exercised here.
