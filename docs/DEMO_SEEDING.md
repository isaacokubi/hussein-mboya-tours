## Supported seed entry point

Use:

`server/scripts/reset-and-seed-demo.js`

The script:

1. Loads the environment from `server/.env`.
2. Requires `CONFIRM_DEMO_RESET=YES`.
3. Requires `SEED_DEMO_PASSWORD` with at least eight characters.
4. Enables `DEMO_SEED_MODE=true` so synthetic records do not trigger external webhook/integration side effects.
5. Preserves platform-owner accounts and existing tenant identities.
6. Clears non-owner application data in the selected database.
7. Recreates deterministic demo users, roles, destinations, tours, packages, vehicles, customers, bookings, payments, commissions, reviews, notifications and leads.
8. Runs the additional finance, operations/website and hospitality/airport demo seeders.

## Mandatory safety gate

**Never run the reset seed against an unknown or real production database.**

Before executing it, verify:

- the current `MONGODB_URI`;
- the MongoDB database name in the URI;
- the deployment/environment;
- that the target is explicitly disposable/staging/demo data;
- that no production tenant or customer data is present.

The seed is intentionally destructive to non-owner application data. A production-looking database name such as `husseindb` must not be treated as disposable merely because the records look synthetic. Require independent confirmation that the target is the authorized demo/staging dataset before allowing a destructive reset.

## Controlled execution

From the repository root:

```bash
cd ~/Desktop/"isaac projects"/"mern stack"/hussein-mboya
cd server

grep '^MONGODB_URI=' .env
grep '^NODE_ENV=' .env || true

CONFIRM_DEMO_RESET=YES SEED_DEMO_PASSWORD='YOUR_DEMO_PASSWORD' npm run seed:demo
```

If the repository does not expose the expected `seed:demo` npm script, inspect `server/package.json` and run the repository's documented command for `reset-and-seed-demo.js`. Do not improvise a destructive command.

## Post-seed verification

After a successful seed:

```bash
cd server
npm test
npm run check:all
```

Then verify:

- all three demo tenants exist;
- expected role accounts can authenticate;
- tenant A cannot access tenant B data;
- tour and destination images are unique;
- booking/payment fixtures exist;
- no live M-Pesa request was made;
- platform-owner credentials were not changed;
- no unrelated production/unknown database was modified.

## Demo credentials

The seed password is supplied through `SEED_DEMO_PASSWORD`. Do not commit it to Git or write it into documentation. The seed's role-specific email convention is generated by the script and should be obtained from the seed output/database rather than hard-coded into source documentation.

## Production boundary

Synthetic seed data is for development, QA, staging and controlled demonstrations. It is not evidence of a successful live payment, KRA/eTIMS submission, SMTP delivery, production backup/restore, or production deployment.
